# ALEPH 08 · 내 소개 페이지에 패스키 달기

> 공개 소개는 누구나 볼 수 있게 유지하고, 개인 학습 공간만 패스키로 잠근 인증 실습 프로젝트입니다.

과제 1에서 만든 자기소개 페이지에 **비밀번호 없는 개인 공간**을 추가했습니다. 화면에서 내용을 숨기는 데 그치지 않고, 서버가 패스키 인증과 자료의 소유자를 확인한 뒤에만 비공개 내용을 내려주도록 구현했습니다.

## 프로젝트 목표

이전 과제에서 비밀번호를 보호하는 인증을 다뤘다면, 이번에는 비밀번호를 없애고 무엇으로 사용자를 확인하는지 실습했습니다.

- 공개 소개와 비공개 자료의 경계를 화면과 서버 양쪽에서 구분하기
- 기기에 보관되는 개인키와 서버에 저장하는 공개키의 역할 이해하기
- 매번 다른 일회용 질문과 서명으로 로그인하기
- 질문 재사용, 잘못된 서명, 다른 계정의 자료 접근을 거절하기
- 예비 패스키와 삭제 처리를 구현하고 복구의 한계 설명하기
- 실제 기기에서 확인한 결과와 자동 검사 결과를 구분해 기록하기

과제 1의 공개 소개 원본은 `public/original/`에 유지했습니다. 이 프로젝트는 초반 자기소개 과제의 확장이며, 별도로 진행한 작전/Defense 자료실 프로젝트와 구분됩니다.

## ① 무엇으로 붙였나

인증은 **SimpleWebAuthn 라이브러리**와 브라우저의 **WebAuthn API**로 구현했습니다. 서명 검증 알고리즘을 직접 새로 작성하지 않고, 질문 보관·세션·권한 검사는 프로젝트 서버 코드에 구현했습니다.

| 구성 | 사용 기술 | 역할 |
| --- | --- | --- |
| 화면 | React · TypeScript · CSS | 공개 소개와 개인 공간, 패스키 관리 |
| 서버 프레임워크 | Vinext | 페이지와 API 라우팅 |
| 브라우저 인증 | `@simplewebauthn/browser` 14.0.0 | 기기의 패스키 등록·로그인 창 호출 |
| 서버 인증 | `@simplewebauthn/server` 14.0.3 | 등록 응답과 로그인 서명 검증 |
| 서버 실행 | Cloudflare Workers | 인증·조회·삭제 요청 처리 |
| 영속 저장 | Cloudflare D1 · Drizzle | 공개키, 일회용 질문, 세션 해시, 가상 자료 보관 |

사이트에는 비밀번호 입력 칸이 없습니다. 기기의 지문·얼굴·PIN 확인은 인증기나 패스키 관리자가 처리하며, 사이트 서버가 비밀번호나 기기 PIN을 받는 방식이 아닙니다.

## ② 왜 그걸 골랐나

패스키의 핵심인 **공개키와 개인키의 분리, 일회용 질문, 서명 검증**을 실제 동작으로 확인하기 위해 선택했습니다.

개인키는 인증기 또는 패스키 관리자가 보관하고 사이트 서버로 보내지 않습니다. 서버에는 credential ID, COSE 공개키의 Base64URL 문자열, 카운터, 패스키 이름, 등록일 등을 저장합니다.

등록은 `attestationType: none`을 사용하므로 장치 제조사에 대한 신뢰 증명을 요구하지 않습니다. 등록 데이터의 질문·Origin·RP ID·사용자 확인을 검사하고, 로그인에서는 저장한 공개키로 서명을 실제 검증합니다.

첫 패스키는 **Google 비밀번호 관리자**에 저장한 것을 실제 등록 창에서 확인했습니다. 저장 위치 선택란은 사용자가 기록하는 정보이며, 그 선택만으로 실제 저장 제공자를 강제하지 않습니다.

## ③ 어디를 어떻게 고쳤나

### 등록부터 조회까지의 흐름

| 흐름 | 요청 경로 | 핵심 구현 |
| --- | --- | --- |
| 등록 | `POST /api/auth/register/options` → `/verify` | 서버 질문 생성·보관 → 기기 등록 → 응답 검증 → 공개키 저장 |
| 로그인 | `POST /api/auth/login/options` → `/verify` | 새 질문 발급 → 기기 서명 → 공개키 검증 → 세션 생성 |
| 로그아웃 | `POST /api/auth/logout` | 서버 세션 삭제와 쿠키 만료 |
| 비공개 조회 | `GET /api/private` | 유효한 세션 확인 후 본인 자료만 반환 |
| 본문 위조 확인 | `POST /api/private` | 요청 본문의 계정 ID를 신뢰하지 않고 세션의 계정으로 조회 |
| 패스키 관리 | `GET /api/passkeys`, `DELETE /api/passkeys` | 본인 키 목록 조회·삭제 |
| 등록 취소 | `POST /api/auth/cancel` | 진행 중인 질문 제거 |
| 증거 조회 | `GET /api/evidence` | 로그인한 계정의 인증·거절 기록 조회 |

브라우저 동작은 [app/private-space.tsx](app/private-space.tsx), API 진입점은 [app/api/[...path]/route.ts](app/api/%5B...path%5D/route.ts), 서버 검사는 [lib/passkey.ts](lib/passkey.ts)에 있습니다.

### 서버에서 확인하는 것

- **일회용 질문:** 매번 새 난수를 만들고 서버에 120초 동안 보관합니다.
- **재사용 차단:** `DELETE ... RETURNING`으로 검증 전에 질문을 원자적으로 소비합니다. 실패한 질문도 다시 사용할 수 없습니다.
- **브라우저 연결:** 질문을 발급받은 브라우저의 쿠키 해시에 묶습니다. 예비 키 등록 질문은 로그인 세션에도 묶습니다.
- **서명 검증:** 질문·Origin·RP ID·사용자 확인을 검사하고, 저장한 공개키로 로그인 서명을 검증합니다.
- **세션:** 256비트 난수 쿠키를 사용하고 서버에는 SHA-256 해시만 저장합니다. 만료 시간은 1시간입니다.
- **쿠키 속성:** `Secure · HttpOnly · SameSite=Strict · Path=/`와 `__Host-` 접두사를 사용합니다.
- **자료 소유권:** 화면이나 요청에 적은 계정 ID 대신 검증된 세션의 계정 ID로 조회합니다.
- **상태 변경 요청:** 정확한 Origin과 JSON 형식을 요구합니다.
- **패스키 삭제:** credential ID와 세션의 소유자를 함께 확인합니다. 마지막 키 삭제 시 해당 계정의 세션과 질문도 폐기합니다.

로그인 전 페이지와 클라이언트 코드에는 비공개 자료의 본문을 넣지 않았습니다. 로그인 후 서버에서만 받아옵니다.

## ④ 안 열리는 것을 확인한 기록

### 실제 브라우저·기기 확인

| 확인 항목 | 결과 | 확인 근거 |
| --- | --- | --- |
| 첫 패스키 등록 | 성공 | Google 저장 완료 화면, 등록한 패스키 1개 |
| 비공개 공간 표시 | 성공 | 로그인 뒤 가상 자료 3개 표시 |
| 로그아웃·재로그인 | 성공 | 사용자 확인 및 실제 기록의 로그인 200 |
| 이미 사용한 질문 재전송 | 차단 | 실제 JSON의 403 `challenge_used_or_unknown` |
| 일부러 바꾼 서명 전송 | 차단 | 서명을 `AAAA`로 바꾼 실제 요청의 403 `verification_failed` |
| 비로그인 상태의 비공개 주소 접근 | 사용자 확인 | 시크릿 창의 `login_required` 표시 보고 |
| 등록 창 취소 | 사용자 확인 | 취소 안내와 잠금 유지 보고 |

마지막 두 항목은 사용자가 직접 실행한 결과를 보고한 내용이며, 최신 원시 응답·화면 파일을 추가로 제출받은 항목과는 구분했습니다. 취소 후 실제 서버 저장 건수가 변하지 않았는지는 자동 검사에서 확인했습니다.

### 자동 검사 결과

**30개 통과 / 실패 0개.** Node.js와 SQLite 어댑터에서 실제 SimpleWebAuthn 검증기를 호출하고, P-256 소프트웨어 인증기로 등록 데이터와 서명을 생성해 검사했습니다.

| 검사 | 허용되는 요청 | 거절되는 요청 |
| --- | --- | --- |
| 인증 여부 | 정상 인증 뒤 본인 자료 조회 → 200 | 로그인 없이 조회 → 401 |
| 계정 분리 | A는 A 자료, B는 B 자료 각 3개 조회 | A → B, B → A 자료 요청 → 각각 403 |
| 계정 ID 위조 | 세션의 본인 계정 자료만 반환 | 다른 계정을 URL에 지정 → 403 |
| 질문 재사용 | 새로운 질문의 정상 서명 → 200 | 같은 로그인 요청 재전송 → 403 |
| 잘못된 서명 | 올바른 P-256 서명 → 200 | 변조한 서명 → 403 |
| 로그아웃 | 유효한 세션으로 조회 → 200 | 로그아웃 전 세션 값 재사용 → 401 |
| 패스키 삭제 | 하나 삭제 후 남은 키 로그인 → 200 | 삭제한 키 로그인 → 403 |

추가로 다른 브라우저의 질문 사용, 만료된 질문, 다른 Origin, 질문이 다른 서명, 타인 패스키 삭제를 거절하는지 검사했습니다. A/B 접근 거절 전후 자료 건수와 내용이 그대로인지도 비교했습니다.

**실제 기기에서 미완료인 항목:** 서로 다른 패스키 2개 등록·하나 삭제 후 로그인, A/B 두 계정의 양방향 자료 접근 차단입니다. 학원 PC의 추가 등록 과정이 USB 보안 키 요구 화면에서 중단되어, 이 항목들은 **자동 검사 통과로만 기록**했습니다. 실제 기기로 모두 완주했다고 표시하지 않았습니다.

## ⑤ AI와 나

- **AI에게 맡긴 일:** 과제 1 원본 확인, 인증과 소유권 검사 코드 작성, 자동 검사 및 설명서 초안 정리.
- **내가 직접 판단한 일:** 작전 과제와 분리해 초반 자기소개 페이지를 확장하도록 정했고, Google 패스키를 선택해 등록·로그인과 차단 검사를 직접 진행했습니다.
- **AI 제안을 따르지 않은 일:** 학원 PC에서 막힌 추가 등록 절차를 계속 반복하는 대신, 실제 기기 미완료 항목을 자동 검사 결과와 구분해 기록하도록 정했습니다.

## ⑥ 아직 못 막은 것과 한계

1. **모든 패스키 분실·삭제 시 복구 불가**  
   비밀번호나 이메일 복구를 만들지 않았습니다. 마지막 키 삭제 전 화면에서 알리고, 삭제 후 기존 세션도 폐기합니다. 새 개인 공간 생성은 이전 공간 복구가 아닙니다.

2. **로그인된 기기를 타인이 사용하는 상황**  
   유효한 세션이 있는 기기를 타인이 사용하면 자료를 읽거나 키를 삭제할 수 있습니다. 키 삭제 직전에 패스키로 다시 인증하게 하는 기능은 아직 없습니다.

3. **운영 수준의 공격·자원 소모 대응 부족**  
   대량 신규 등록과 질문 발급에 대한 속도 제한, 자동 데이터 정리, 악성 확장 프로그램이나 XSS에 의한 세션 악용을 모두 해결하지 못했습니다.

4. **실제 기기 시험의 범위**  
   예비 키 삭제와 A/B 계정 시험은 자동 검사로만 확인했습니다. 실제 기기의 완주 증거를 대신한다고 주장하지 않습니다.

교육용 가상 자료를 대상으로 제작했으며, 실제 민감정보를 보관하는 서비스로 검증한 프로젝트는 아닙니다.

## 짧은 확인 방법 · 4줄

- **어디로 가나요:** 결과물 주소를 열고 공개 소개 아래의 **개인 공간**으로 이동합니다.
- **세 단계 안에 무엇을 하나요:** ① 개인 공간 이동 → ② 로그인 없는 요청 확인 → ③ 요청·응답 기록 펼치기.
- **무엇이 보이면 통과인가요:** 공개 소개는 보이고 비공개 본문은 보이지 않으며, `GET /api/private`가 401로 거절됩니다.
- **안 될 때는 무엇이 보이나요:** 연결 오류 안내가 나오거나, 인증하지 않았는데 200으로 비공개 본문이 반환되면 실패입니다.

## 검사 실행

Node.js 24 이상과 프로젝트 의존성이 필요합니다. 저장소를 내려받아 의존성을 설치한 뒤 실행합니다.

```bash
pnpm install --frozen-lockfile
node --experimental-transform-types tests/passkey.test.mjs
node node_modules/typescript/bin/tsc --noEmit
```

자동 검사는 메모리의 SQLite에서 실행되며 운영 DB에 자료를 추가하지 않습니다. 실행하면 자동 검사 증거 JSON을 다시 생성합니다. 위 결과는 기존 제작 과정에서 확인한 결과이며, README 수정만을 위해 실제 기기 시험을 다시 실행한 것은 아닙니다.

## 배포 및 이전 시 주의점

공개 서비스는 Cloudflare Workers와 D1을 연결한 환경에서 동작합니다. 이 GitHub 저장소는 제출·검토용 소스 저장소이며 **GitHub에 push하는 것만으로 현재 서비스가 자동 배포되도록 연결한 것은 아닙니다.**

Vercel이나 GitHub Pages에 정적 파일만 올리면 인증 API와 DB가 함께 동작하지 않습니다. 다른 주소로 이전하려면 서버·DB 설정과 `app/api/[...path]/route.ts`의 고정 Origin 및 RP ID 구성을 함께 맞춰야 합니다. 등록된 패스키는 RP ID에 묶이므로 새 도메인에서 그대로 사용할 수 있다고 가정하면 안 됩니다.
