# ALEPH 과제 8 — 내 소개 페이지에 패스키 달기

결과물: https://yc-aleph-08-passkey.ksyji123.chatgpt.site/
소스: https://yc-aleph-08-passkey.ksyji123.chatgpt.site/source
과제 1 원본: https://github.com/ychanis/ALEPH_01

초반 자기소개 과제에 이어 붙인 별도 ALEPH_08입니다. 작전/Defense 자료실 과제와 관계없는 새 프로젝트입니다. 과제 1의 index.html, style.css, script.js를 public/original/에 그대로 보관하고 첫 화면에 표시합니다. 기존 공개 소개 내용은 유지했습니다. 새로운 비공개 내용은 프로젝트 준비 메모·지원 계획 연습·학습 회고 3개이며 모두 만들어 넣은 가상 자료입니다. 계정마다 다른 식별자를 붙여 서로 다른 내용을 제공합니다. 실제 연락처·주소·신분증 번호·비밀번호·운영 비밀값은 없습니다.

## ① 무엇으로 붙였나

인증 검증은 직접 암호 알고리즘을 새로 만들지 않고 라이브러리 SimpleWebAuthn을 사용했습니다. @simplewebauthn/server 14.0.3이 등록 응답 및 로그인 서명을 검사하고, @simplewebauthn/browser 14.0.0이 브라우저의 WebAuthn API를 호출합니다. 프레임워크는 React와 Vinext, 서버는 Cloudflare Workers, 저장소는 D1입니다. 계정 분리·일회용 질문 관리·세션·로그아웃·비공개 자료 조회는 lib/passkey.ts에 구현했습니다. 외부 OAuth나 비밀번호 인증 서비스를 사용하지 않습니다.

기기가 생성한 개인키는 사이트 서버에 전송하지 않습니다. 서버에는 credential ID, COSE 공개키의 Base64URL 문자열, 카운터, 패스키 이름, 등록 날짜 등을 저장합니다. 등록 기록의 attestationObject는 공개키와 인증기 정보를 포함하며 개인키가 아닙니다. attestationType은 none이므로 장치 출처 증명 대신 표준 WebAuthn 등록 데이터의 challenge·Origin·RP ID·사용자 확인을 검사합니다. 로그인에서는 공개키로 서명을 실제로 검증합니다.

## ② 왜 그걸 골랐나

브라우저·기기가 제공하는 패스키를 사용하고 공개키·서명 검증을 검증된 라이브러리에 맡기기 위해 선택했습니다. 비공개 자료를 HTML에 넣고 화면에서만 감추는 방식은 사용하지 않았습니다. 서버가 인증한 세션의 계정 ID로만 자료를 조회하며, 공개 소개와 설명서·소스는 로그인 없이 열립니다. 패스키 창의 기기 PIN이나 생체 인증은 기기가 처리하고 이 사이트는 입력받지 않습니다.

## ③ 어디를 어떻게 고쳤나

| 흐름 | 브라우저 소스 | 서버 경로 | 확인하는 위치 |
| --- | --- | --- | --- |
| 등록 | app/private-space.tsx의 register | POST /api/auth/register/options → /verify | lib/passkey.ts의 issue·consume·verifyRegistrationResponse |
| 로그인 | app/private-space.tsx의 login | POST /api/auth/login/options → /verify | lib/passkey.ts의 verifyAuthenticationResponse·newSession |
| 로그아웃 | app/private-space.tsx의 logout | POST /api/auth/logout | lib/passkey.ts의 sessions DELETE 및 쿠키 만료 |
| 비공개 조회 | app/private-space.tsx의 refresh·cross | GET 또는 POST /api/private | lib/passkey.ts의 session 및 WHERE owner = 세션.owner |
| 패스키 목록·삭제 | app/private-space.tsx의 remove | GET·DELETE /api/passkeys | lib/passkey.ts의 WHERE id = ? AND owner = ? |

모든 API 진입점은 app/api/[...path]/route.ts입니다. 테이블은 db/schema.ts와 drizzle/0000_abandoned_random.sql에서 확인합니다. 공개 소개 원본은 public/original/에 있습니다.

질문은 서버에서 매번 새 난수로 생성하고 D1에 120초 동안 저장합니다. 질문을 받은 브라우저의 HttpOnly 쿠키 해시에 묶으며, 예비 키 등록은 인증된 세션에도 묶습니다. verify 처리에서는 DELETE ... RETURNING으로 질문을 원자적으로 먼저 소비하므로 실패한 질문도 다시 쓰지 못합니다. Origin·RP ID·사용자 확인을 검증합니다. 상태 변경 요청에는 정확한 Origin과 JSON을 요구합니다.

로그인 뒤에는 256비트 난수 세션 쿠키를 사용합니다. 쿠키는 Secure, HttpOnly, SameSite=Strict, Path=/이며 __Host- 접두사를 사용합니다. 서버에는 원문 대신 SHA-256 해시와 계정 ID·1시간 만료 시간을 저장합니다. 로그아웃하면 서버 세션을 지워서 이전 값을 다시 사용해도 401이 됩니다. 제출 기록에는 세션·쿠키·일회용 ticket 값을 [REDACTED]로 가립니다.

처음 등록할 때 서버가 무작위 계정을 새로 만들며 다른 계정을 지정할 수 없습니다. 예비 패스키는 로그인된 본인 계정에만 추가됩니다. GET의 다른 accountId는 403으로 거절하고, POST 본문에 다른 accountId를 넣어도 이를 신뢰하지 않아 내 자료만 반환합니다. 다른 패스키로 정상 인증하면 그 패스키의 계정으로만 로그인할 수 있습니다.

패스키 저장 위치는 기기 자체·Google 비밀번호 관리자·보안 키·기타 중 실제 선택한 위치를 사용자가 적습니다. 사이트가 저장 제공자를 자동으로 확인한 것으로 주장하지 않습니다. Google·Apple 등의 동기화 패스키는 여러 기기에 보일 수 있으므로 두 기기에서 같은 키를 사용하는 것과 서로 다른 키 두 개를 등록하는 것을 구분합니다.

## ④ 안 열리는 것을 확인한 기록

현재 자동 검사: 30개 통과, 실패 0개. tests/passkey.test.mjs가 실제 P-256 서명을 생성하고 실제 SimpleWebAuthn 검증기를 호출합니다. SQLite 어댑터로 서버의 SQL을 실행했습니다. 이것은 실제 영찬님 기기나 배포 서버에서 수행한 검사와 구분됩니다. 상세 요청·응답과 저장 공개키는 docs/automated-evidence.json에 있습니다. 테스트용 개인키는 메모리에서만 생성하며 저장하지 않았습니다.

| 확인 | 통과 요청 | 거절 요청 |
| --- | --- | --- |
| 로그인 없이 열기 | 등록·로그인 뒤 GET /api/private → 200, 본인 자료 3개 | 세션 없이 동일 GET → 401 login_required |
| 남의 패스키·자료 | A 서명으로 로그인 → 200, A 자료만 3개 | A 세션의 GET /api/private?accountId=B → 403 owner_mismatch; B → A도 403 |
| 이미 쓴 질문 | 새 질문에 대한 정상 P-256 서명 → 200 | 성공한 로그인 본문을 그대로 재전송 → 403 challenge_used_or_unknown |
| 패스키 삭제 뒤 로그인 | A에 두 개 등록, 첫 키 삭제 후 예비 키 로그인 → 200 | 삭제한 credential ID의 로그인 → 403 passkey_unknown_or_deleted |

양방향 자료 접근 거절 전후 A=3개, B=3개이며 내용도 동일했습니다. 본문 accountId=B를 보낸 A의 요청은 200이지만 반환된 계정과 자료는 A였습니다. 변조한 서명은 403, 잘못된 Origin과 challenge도 403입니다. 로그아웃 전 세션 값을 다시 사용하면 401이며 마지막 키를 삭제하면 기존 세션도 폐기됩니다. 등록 취소 뒤 계정·패스키가 저장되지 않았습니다. 등록과 로그인 질문이 각각 서로 다른 값인 기록, 등록 요청 본문, 실제 저장한 공개키는 JSON에 있습니다.

실제 기기 확인 결과 (2026-10-22 정리): Google 비밀번호 관리자에 첫 패스키를 등록했고, 등록한 키의 이름·등록일·공개키 목록과 가상 메모 3개가 보이는 화면을 확인했습니다. 로그아웃·재로그인 성공은 사용자 확인 및 제출된 실제 브라우저 기록으로 확인했습니다. 제공받은 JSON에는 정상 로그인 200, 질문 재사용 403 challenge_used_or_unknown, 서명을 AAAA로 바꾼 요청 403 verification_failed가 있습니다. 실제 기록과 화면을 확인한 항목입니다.

사용자가 별도로 확인한 항목: 시크릿 창에서 /api/private에 접속했을 때 login_required가 표시됐고, 등록 창을 취소했을 때 취소 안내와 잠금 유지가 확인됐다고 보고했습니다. 이 두 항목의 최신 원시 응답·화면 파일은 추가 제출받지 않았습니다. 등록 취소 뒤 서버 저장 건수 불변은 자동 검사에서 확인한 결과이며, 실제 기기의 DB 건수를 직접 확인한 것으로 표시하지 않습니다.

실제 기기에서 미완료인 항목: 서로 다른 패스키 두 개 등록, 하나 삭제 뒤 남은 키 로그인·삭제한 키 거절, A/B 두 계정의 양방향 접근 거절과 건수 비교입니다. 학원 PC에서 추가 등록을 시도했으나 USB 보안 키 요청 화면에서 진행하지 못했습니다. 위 항목은 소프트웨어 인증기를 사용한 자동 검사 통과로만 기록합니다. 실제 키 두 개 등록 또는 실제 삭제를 완료했다고 쓰지 않았습니다. 이 구분은 과제의 실제 기기 완주 조건을 모두 충족했다는 뜻은 아닙니다.

## ⑤ AI와 나

AI에게 맡긴 일: 과제 1 원본 확인, 패스키 등록·로그인·로그아웃·비공개 조회 코드, 자동 보안 검사와 설명서 초안 제작.
내가 직접 판단한 일: 이번 과제가 초반 소개 페이지 과제이며 작전 과제와 별개라는 점을 정하고, 기존 소개를 찾아 이어 붙이도록 요청한 일.
AI 제안을 따르지 않은 일: 학원 PC에서 추가 패스키 등록이 USB 보안 키 요구로 막혔을 때 같은 등록 절차를 더 반복하지 않고, 해당 실제 기기 시험은 미완료로 남기고 자동 검사 결과와 구분해 제출문을 정리하기로 판단했습니다.

## ⑥ 아직 못 막은 것

패스키를 모두 잃거나 마지막 키까지 삭제하면 기존 공간을 복구하지 못합니다. 비밀번호·이메일 복구는 의도적으로 만들지 않았습니다. 마지막 삭제 전 화면에서 다시 알리고 삭제 후 모든 세션과 해당 계정 질문을 폐기합니다. 새로운 공간 등록은 이전 공간의 복구가 아닙니다.

이미 로그인된 기기를 타인이 쓰면 유효한 세션으로 자료를 읽거나 키를 삭제할 수 있습니다. 패스키 삭제 직전에 별도의 재인증을 강제하는 기능은 아직 없습니다. XSS나 브라우저 악성 확장에 의한 세션 악용을 모두 해결하지 못합니다. 또한 대량 신규 등록·질문 발급에 대한 운영 수준의 속도 제한과 자동 데이터 정리는 구현하지 않았습니다. 가상 자료를 넣는 교육용 과제이며 실제 민감정보 보관 용도로 확장하지 않았습니다.

## 짧은 확인 방법 — 4줄

어디로 가나요: 결과물 URL의 첫 화면은 공개 소개이며 아래 '개인 공간'으로 이동합니다. 설명서와 소스도 로그인 없이 볼 수 있습니다.
세 단계 안에 무엇을 하나요: ① 개인 공간으로 이동 ② '로그인 없는 요청 확인' 클릭 ③ 과제 확인 기록 펼치기.
무엇이 보이면 통과인가요: 공개 소개가 보이고 비공개 본문은 보이지 않으며 GET /api/private 기록이 401입니다.
안 될 때는 무엇이 보이나요: 연결 오류 안내가 뜨거나 200으로 비공개 자료가 열리면 실패입니다. 정상 인증 실패는 401·403 안내로 표시됩니다.
